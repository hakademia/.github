# Contributing to Hakademia

**Version:** 1.0  
**Status:** Proposed

Thank you for your interest in contributing to Hakademia!

Hakademia is a developer-focused organization dedicated to coding competitions, developer tools, open-source projects, and collaborative innovation.

We welcome contributions from developers of all experience levels.

## 1. Ways to Contribute

You can contribute by:

- Developing features and fixing bugs .
- Improving documentation and examples.
- Creating plugins, SDKs, and integrations.
- Reporting bugs and suggesting improvements.
- Reviewing code and helping other contributors.
- Participating in hackathons and coding competitions.
- Building new community projects.

## 2. Our Project Structure

Hakademia operates through three development circles.

### Core Team

Responsible for the core platform, infrastructure, architecture, and security.

Core repositories may be private and require explicit authorization.

### Ecosystem Team

Develops plugins, SDKs, integrations, and supporting tools.

Ecosystem repositories may be public or private, depending on project requirements and organization permissions.

### Community Team

Creates public open-source projects, hackathon submissions, and experimental tools.

Community members should use the official `community-template` when starting new projects.

External contributors may contribute to accessible projects through Issues and Pull Requests.

## 3. Getting Started

1. Explore Hakademia's public repositories.
2. Read the project's README and documentation.
3. Review existing Issues and Pull Requests.
4. Choose an issue or propose an improvement.
5. Follow the repository's contribution instructions.
6. Submit your contribution for review.

For major changes, open an Issue or Discussion before beginning implementation.

## 4. Development Workflow

### Forking and Branching

If you do not have write access, fork the repository and create a branch in your fork.

If you have write access, create a dedicated branch in the repository.

Use descriptive branch names:

```text
feature/add-leaderboard
fix/authentication-error
docs/update-api-guide
refactor/competition-engine
test/add-unit-tests
```

Avoid committing directly to protected branches such as `main`.

### Making Changes

- Keep changes focused and understandable.
- Follow the project's existing coding conventions.
- Add or update tests when appropriate.
- Update documentation when behavior changes.
- Avoid unrelated modifications.
- Never commit credentials, secrets, or sensitive data.

### Commit Messages

We recommend Conventional Commits:

```text
feat: add competition leaderboard
fix: resolve login validation issue
docs: update installation instructions
refactor: simplify tournament service
test: add authentication tests
chore: update dependencies
```

Keep commit messages clear and descriptive.

## 5. Pull Requests

Before submitting a Pull Request:

- Ensure the project builds successfully.
- Run relevant tests and checks.
- Review your changes for accidental files or secrets.
- Update documentation when necessary.
- Link related Issues when available.
- Explain what changed and why.

Pull Requests should be reviewed by authorized maintainers before merging.

Approval requirements may differ between Core, Ecosystem, and Community repositories.

## 6. Code Review

Reviews should focus on:

- Correctness and functionality.
- Readability and maintainability.
- Security and reliability.
- Performance where relevant.
- Test coverage.
- Compatibility with project requirements.

Reviewers should provide constructive feedback.

Contributors should respond respectfully and make reasonable adjustments when necessary.

## 7. Creator Recognition and Attribution

Hakademia recognizes original creators, maintainers, and contributors.

Each project should identify its original creator or creators in its documentation.

The `AUTHORS.md` file may include:

- Original creators.
- Current maintainers.
- Significant contributors.

Git commit history should be preserved whenever practical.

Contributors must not falsely claim authorship or remove required attribution.

Contribution does not automatically transfer copyright ownership to Hakademia. Applicable licenses and agreements determine the rights granted.

## 8. Documentation Standards

Every repository should include, at minimum:

- `README.md` — Project description, setup, and usage.
- `LICENSE` — Applicable license, when the project is intended for open-source distribution.
- `AUTHORS.md` — Creator and contributor recognition.
- `CONTRIBUTING.md` — Contribution guidelines, either local or inherited from the organization.

Additional documentation may be required for SDKs, plugins, and production services.

## 9. Security

Do not disclose security vulnerabilities publicly before responsible coordination.

Follow the instructions in `SECURITY.md`.

Never commit secrets, access tokens, passwords, or private keys.

Report suspected vulnerabilities through the designated security contact.

## 10. Community Standards

All participants must follow Hakademia's `CODE_OF_CONDUCT.md`.

We expect respectful communication, fair collaboration, and proper recognition of others' work.

Harassment, plagiarism, abuse of permissions, and deliberate sabotage are prohibited.

## 11. Licensing

Contributions must comply with the repository's license and any applicable contribution agreements.

Do not submit code, documentation, or other material that you do not have permission to contribute.

Different projects may use different licenses.

## 12. Questions and Support

For project-specific questions, use the repository's Issues or Discussions when enabled.

For community questions, contact the appropriate project maintainers.

For conduct-related reports, contact **conduct@hakademia.dev**.

For security vulnerabilities, contact **security@hakademia.dev**, once the address is active, or use the repository's private vulnerability reporting feature when available.

## 13. Governance

Hakademia projects operate under the organization's governance policies.

Maintainers and contributors should respect repository ownership, access controls, project decisions, and creator recognition requirements.
